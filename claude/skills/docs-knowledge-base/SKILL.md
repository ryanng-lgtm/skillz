# docs-knowledge-base — nested markdown docs with generated indexes

## Overview

A plain-markdown docs directory that an agent can navigate cheaply, the same
way it navigates skills: read a short index of descriptions, then open only
the doc that matches. It is the source of truth for "what exists" (apps,
infra, data contracts, decisions). Agent memory only holds a one-line pointer
to it.

Three ideas carry the whole system:

1. **Nesting:** top `INDEX.md` → `<area>/INDEX.md` → `<area>/NNN Title.md`, with optional
   sub-areas (`<area>/<sub>/INDEX.md` → `<area>/<sub>/NNN Title.md`) at any depth.
   Tokens spent are driven by the size of the doc actually read, not by
   folder depth.
2. **Frontmatter:** every doc declares `description`, `tags`, `status`,
   `updated`. Every area `INDEX.md` declares `description`, `tags`, `related`.
3. **Generated indexes:** `scripts/build-index.py` rebuilds the tables in
   every `INDEX.md` from that frontmatter and validates links, so the index
   never drifts from the docs.

The full spec lives in the docs dir's own `CLAUDE.md` (a copy ships as
`templates/conventions.md`). It is authoritative. This skill covers the
workflow.

**Core principle: every fact has one home doc, and every index is generated
from frontmatter, never edited by hand.**

## Files in this skill

- `scripts/build-index.py`: the index generator and checker (stdlib only,
  Python 3.8+).
- `templates/conventions.md`: the conventions spec. Copy it into the docs
  root as `CLAUDE.md`. It ships under another name so this repo's agents
  don't load it as their own instructions.
- `templates/INDEX.md`: the top-level index skeleton.
- `templates/area-INDEX.md`: an area index skeleton.
- `templates/doc.md`: a numbered doc skeleton.
- `references/imported-markdown-cleanup.md`: repairing docs converted from
  Word/Google Docs.

## Layout

```
<docs>/
  INDEX.md                 how to look things up + GENERATED area table
  ABOUT.md                 the owner's personal context and working preferences
  CLAUDE.md                conventions (frontmatter spec, numbering, links)
  scripts/build-index.py   regenerates every INDEX table; --check validates
  <area>/INDEX.md          area frontmatter + reading order + GENERATED doc table
  <area>/NNN Title.md      docs, numbered per area from 001
  <area>/TMP Title.md      temporary handoffs: no number, no frontmatter
  <area>/<sub>/...         optional sub-area: same shape, own INDEX.md and numbering
```

- An **area** is one project or one infra domain, named in lowercase
  kebab-case (`calorie-tracker/`, `k3s/`). Create it with its first doc.
  Numbered docs never sit at the top level.
- **Sub-areas** nest a specific effort under a general area, e.g.
  `shopping/` (shop access and browsing, reusable for any product) with
  `shopping/clothes-hunting/` (one hunt's brief and leads). Use one for that
  general/specific split, or once an area passes roughly 10 docs.
  - The script recurses to any depth, giving the parent INDEX a generated
    sub-area table. The top-level table lists only top areas, with their
    counts including sub-areas.
  - Refs: `[clothes-hunting/001]` from the parent, or
    `[shopping/clothes-hunting/001]` from elsewhere, each with a relative
    link definition.
  - Moving docs into a new area renumbers them per folder. Update every ref
    and run `--check`.

## Setting up a new docs dir

```bash
DOCS=~/workspace/docs
SKILL=~/.claude/skills/docs-knowledge-base   # ~/.codex/skills/... under Codex
mkdir -p "$DOCS/scripts"
cp "$SKILL/scripts/build-index.py" "$DOCS/scripts/"
cp "$SKILL/templates/conventions.md" "$DOCS/CLAUDE.md"
ln -s CLAUDE.md "$DOCS/AGENTS.md"            # Codex reads AGENTS.md
cp "$SKILL/templates/INDEX.md" "$DOCS/"
touch "$DOCS/ABOUT.md"
cd "$DOCS" && git init -b main && git add -A
```

Then commit through the `commit` skill.

For each area: `mkdir "$DOCS/<area>"`, copy `templates/area-INDEX.md` to
`<area>/INDEX.md`, and fill in its frontmatter. Then write
`<area>/001 Title.md` from `templates/doc.md` and run the script. The doc
template's example `[002]`/`[other-area/001]` links point at files that
don't exist, so `--check` reports them as broken until you replace or
delete them.

Add a one-line memory pointer, e.g. "Docs live at ~/workspace/docs/
(conventions in CLAUDE.md there). Skim INDEX.md/ABOUT.md before substantial
work; record durable things the same turn."

## Frontmatter

Doc:

```yaml
---
description: "What's in it and when to read it, in one or two sentences. Name the concrete things someone would search for."
tags: [area-name, topic, tool, table-name]
status: current            # or: superseded by NNN
updated: YYYY-MM-DD
host: myhost (192.168.0.10)   # optional
---

# Title
```

Area `INDEX.md`: `description`, `tags`, `related:` (skills, cron jobs, URLs,
repo paths as one quoted string), and optionally `improvement:` and
`tooling:` (see "Continuous improvement" in `CLAUDE.md`). Under it go a line
or two of reading order ("read 002 before any deploy") and the GENERATED
markers.

- **`description` matters most.** Write it for a reader who doesn't know the
  doc exists, naming the concrete terms they'd search for. Rewrite it in the
  same edit whenever the doc's scope changes.
- Tags are lowercase kebab-case, and the **area comes first**.
- Always quote `description`. Don't nest escaped quotes inside it, because
  they render as `\"` in the generated table.
- The parser is deliberately tiny: one `key: value` per line, lists as
  `[a, b]` or as `- item` lines under the key (the form Obsidian's Properties
  editor writes), `#` comment lines skipped. Don't use other multi-line YAML.

## Filenames and links

- `NNN Title In Title Case.md`: zero-padded, numbered **per area** in order
  of creation from `001`. Next number = highest in that folder + 1. **Never
  reuse or renumber**, because the number is an identity, not a ranking.
- Filenames use spaces, so quote paths in shell commands.
- Use reference-style cross-links, with the definitions at the bottom of
  the doc. In an Obsidian vault, use the vault's link style instead (see
  "Obsidian vaults").
  - same area: `[002]` with `[002]: ./002%20Title.md`
  - across areas: `[k3s/002]` with `[k3s/002]: ../k3s/002%20Title.md`
- `TMP Title.md` holds handoffs, briefs and questions for another agent or
  a human. The script ignores it. Never cite it as a source of truth. Fold
  its lasting facts into a numbered doc, then delete it.

## Obsidian vaults

The docs dir can be an Obsidian vault or a folder inside one. The script
finds the vault (the nearest `.obsidian/` at or above the docs root) and
checks links the way Obsidian resolves them:

- **Wikilinks and embeds:** `[[Title]]`, `[[area/001 Title|text]]`,
  `[[Title#Heading]]`, `![[diagram.png]]`. A bare name must match exactly one
  note in the vault. One that matches several is reported; give it a path.
- **Markdown links:** relative to the doc, from the vault root, or by a
  filename unique in the vault, which covers each of Obsidian's "New link
  format" settings. Outside a vault, markdown links resolve relative to the
  doc only.

Keep the vault's existing link style rather than converting it. Obsidian
does not treat reference-style definitions (`[002]: ./002%20Title.md`) as
internal links, so they miss its graph, backlinks and rename updates.

Move or rename docs inside Obsidian when you can: with "Automatically update
internal links" on, it rewrites every link to the file. After a scripted
move, `--check` lists the links it left behind. If iCloud has offloaded
notes to save space, `--check` reports links to them as broken; download the
folder first.

## The script

```bash
python3 <docs>/scripts/build-index.py            # rewrite the GENERATED tables
python3 <docs>/scripts/build-index.py --check    # validate only, write nothing
python3 build-index.py --root ~/somewhere/docs   # or DOCS_ROOT=...; default = parent of scripts/
```

It only rewrites the text between `<!-- BEGIN GENERATED
(scripts/build-index.py) -->` and `<!-- END GENERATED -->`, so hand-written
prose in an `INDEX.md` is safe. It exits 1 and prints `PROBLEM:` lines for:

- a doc with no frontmatter, or missing `description`/`tags`/`status`/
  `updated`
- an area `INDEX.md` missing `description`/`tags`, or missing the markers
- an `[NNN]` or `[area/NNN]` used but not defined (fenced and inline code
  are ignored)
- a markdown link or wikilink whose target doesn't exist, or a bare name
  that matches several files in an Obsidian vault
- a numbered doc at the top level
- an index that is out of date (`--check` only)
- `improvement:` not in (`continuous`, `off`), or set on a doc rather than
  an area
- a `continuous` area with no `tooling:` dir, a dir outside git, or a dir
  missing `README.md`, `tests/` or `BY-HAND.md`

It does **not** flag unnumbered, non-`TMP` files inside an area (e.g. a
leftover import stub). List the folder yourself.

## Looking something up

1. Read `INDEX.md`, then the matching `<area>/INDEX.md`, then only the doc
   that matches.
2. For a blind search, grep `^(description|tags):.*<term>` over the docs
   dir, or search the full text for a specific identifier.

## Writing or updating docs

1. **Facts, not a ledger.** Record the current state, rules, contracts,
   decisions with their one-line reason, commands that work, measured
   numbers (and when they were verified), and gotchas that cost real time.
   Never record session history: milestone narratives, bugs fixed and
   forgotten, processes killed, files moved. Git holds the history.
2. **Loose shape:** decision/outcome → setup (paths, config, exact commands)
   → gotchas.
3. **Update in place and bump `updated`.** For a reversed decision, write a
   new doc, set the old one to `status: superseded by NNN`, and link forward.
4. **Split by what gets loaded together.** When part of a doc is regularly
   needed on its own, give it its own doc and leave a pointer. A
   single-topic doc that is read end to end stays whole, even at 10+ KB.
5. **One home per rule.** Put a fact where its topic lives, and have other
   docs link to it (`[k3s/002]`) instead of restating it. When a decision
   changes a cross-cutting rule, edit the rule in its home doc.
6. **Standing preferences about how the owner works go in `ABOUT.md`.**
   Per-project facts go in area docs. Per-repo working notes go in that
   repo's own `CLAUDE.md`.
7. **Record the decision, not private context.** If the owner explains a
   decision with background they don't want written down, write only the
   rule with a neutral one-line reason.
8. **Define any term you coin** in the doc where it first appears.
9. **Write agreed additions into the file in the same turn.** Don't say
   "I'll fold it in later". The file is the single state.
10. Run the script, then `--check`. Fix every problem, and list any new
    area folder for strays.
11. **Commit:** stage the docs you changed and commit through the `commit`
    skill, with a message like `<area>: <what changed>`.
12. **Chase references outside the docs** after any move or rename: skills,
    memory, cron job prompts, and code comments that mention the docs path.
    Update them all in the same pass.

**Scripted multi-doc edits:** use a `rep` helper that asserts exactly one
match before replacing. Build every edit in memory, then write all files at
the end, so a failed assert leaves nothing half-applied. If the scripting
environment can lose state between runs, keep the helpers in a module file
and import it at the top of each run.

## Restructuring (moving or renumbering many docs)

- Start from a clean, committed tree so the whole move can be reverted.
- Do it in one script:
  1. Build an old → (area, new number, title) map.
  2. Strip old headers and prepend frontmatter.
  3. Rewrite `[NNN]` refs through placeholders so renumbering can't collide.
  4. Regenerate the link definitions.
- Test the checker on a scratch copy with deliberately broken docs, to
  confirm it catches each class of error.

## TMP round trip (questions → decisions)

- **Writing the TMP:** make `<area>/TMP <Title>.md` standalone for a reader
  with no view of the conversation. Open with a short context paragraph,
  list the decisions already made, then give each open question its options
  and a suggested default.
- **Folding answers back:** put each decision into its topic doc, not a new
  "decisions" doc. Rewrite superseded requirements in place, and move
  deferred ones to a "Later" section with their reason. Update
  `description`/`tags`, grep the area for stale terms, then delete the TMP
  in the same commit.
- **Partial answers:** fold the settled items in now. The TMP keeps only the
  delegated items, each with a **Suggestion** and **Questions** block.
- **Report guesses:** anything you invented while folding is listed in the
  report as a guess to confirm.

## Cross-app backlogs

When features across several apps wait on the same infra change (e.g.
HTTPS), keep one list in the infra area, with items per app and a checklist
for the switch. App docs link to it rather than keeping their own lists.

## Continuous improvement (opt-in per area)

`improvement: continuous` plus `tooling: <dir>` in an area's `INDEX.md`
lets the agent extend that project's tooling dir without asking. Only the
owner sets the flag. The rules are in `CLAUDE.md`:

- the tooling dir must be in git and hold `README.md`, `tests/` and
  `BY-HAND.md`
- build a feature on its second by-hand occurrence
- tests pass before every commit, and commits start with the agent's
  prefix (e.g. `hermes:`)
- migrations, deploys, data deletion, new crons and new dependencies still
  need approval
- mention each change in one line of the reply

## Answering "should we restructure X?"

Weigh three things, then recommend:

- **What it saves.** Tokens are driven by the size of the doc read.
- **What it costs.** Every extra file or step has to be kept in sync.
- **What goes stale.** Hand-kept indexes drift; generated ones don't.

Push back on ceremony (e.g. a sub-index in every folder regardless of
size). When the owner proposes a better model, say so and build on it.

## Reporting

Keep it short:

- new docs, one line each
- updated docs and what changed
- what was split, and why
- references fixed outside the docs
- the checker result
- the size of `INDEX.md`, and the growth point where you'd nest further
